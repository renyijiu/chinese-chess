# WebRTC 好友直连模式

好友直连是一个默认关闭的实验性休闲对局模式。两台浏览器通过一条可靠、有序的 `RTCDataChannel` 交换棋局命令；部署方不需要提供匹配大厅、账户系统或权威游戏服务端。首版的目标是让互相信任的朋友完成一盘棋，而不是提供竞技平台级可靠性。

## 启用与网络配置

构建或启动应用时设置：

```bash
NEXT_PUBLIC_XIANGQI_ONLINE_ENABLED=1
```

未设置、设为 `0` 或其他值时，开始菜单不显示在线入口。可用逗号分隔配置最多八个公共或自有 STUN URL：

```bash
NEXT_PUBLIC_XIANGQI_STUN_URLS=stun:stun.example.com:3478,stun:stun-backup.example.com:3478
```

首版只接受无空白的 `stun:` URL；其他 scheme、超长项、重复项和超过上限的项会被忽略。空配置会尝试无 STUN 的主机候选直连，通常只适用于同一局域网或浏览器能够直接互达的环境。

首版不提供 TURN。对称 NAT、严格防火墙、企业网络、VPN 或 UDP 受限环境可能无法建立连接；应用会显示失败并允许重新配对，但不会把棋局流量转发到应用后端。部署检查应至少覆盖同一局域网、常见家庭 NAT，以及一个确定会失败的无中继替身环境。

生产部署应保持 HTTPS 安全上下文；当前 Cloudflare Worker 形态不需要为棋局增加数据库、WebSocket 或 Durable Object。能正常加载网页并不代表任意两种网络都能建立 WebRTC 直连。

## 手动 non-trickle 信令流程

首版没有房间码服务。每次新连接或刷新后的恢复都完整执行一次手动交换：

1. 房主选择“创建邀请”。浏览器创建 DataChannel 与 Offer，并等待 ICE gathering complete；完成前不要复制半成品。
2. 房主复制完整 Offer 邀请文本，或使用系统分享，只发送给本局好友。文本不超过 2 KiB 时也可按需显示二维码，但二维码只是辅助，不取代可校验的完整文本。
3. 加入方选择“加入棋局”，粘贴 Offer，等待自己的 ICE gathering complete，然后复制、分享或在长度允许时展示完整 Answer 响应文本。
4. 房主粘贴 Answer。双方等待 DataChannel 打开并完成 `hello`/状态核对。
5. 两边分别点击“我已准备”。双方状态一致且都准备后才开放棋盘输入。

Offer/Answer 默认十分钟过期。它们是一次性配对材料，不应发到公开群聊、长期保存或提交到日志和问题追踪系统。成功连接、取消或开始重新配对后，应用会清除页面内信令；用户也应清理剪贴板历史和聊天中的文本副本。应用不会把 SDP/ICE 写入棋局存档。

首局由房主执红、加入方执黑。终局后任何一方可发起重开；双方同意后复用已打开的 DataChannel，生成新的 `matchId` 并交换红黑。联机模式不支持悔棋。

## 传输内容与一致性边界

DataChannel 只承载版本化的棋局协议消息，不同步棋子 3D 坐标、动画、VFX 或音频。视觉与声音都由每端根据已经确认的规则事件独立表现，失败也不得改变规则状态。

协议 v1 包括：

- `hello`、`ready`：协商规则/能力，核对棋局身份、revision 与 position hash，并建立双方准备屏障。
- `command`、`ack`：提交一手着法及其 `expectedRevision`、前后 position hash，并确认应用或幂等重复。
- `snapshot-request`、`snapshot`：仅用于重新配对或检测到一致性缺口时的受限恢复。
- `ping`、`pong`：携带 `heartbeat` 或 `revalidation` 用途并探测双方 revision/hash；日常心跳可核对已知历史前缀，断线/后台恢复则要求当前状态严格相等，超时会锁定输入。
- `resign`：请求并提交可发生在任意轮次的认输，避免与同时发生的走子产生两个终局。
- `rematch`：终局后的请求、接受、拒绝或取消，携带终局 revision/hash 与下一局身份。
- `error`：报告版本、身份、顺序、schema、大小、频率或状态恢复错误。

只有当前执子方可以发送着法；对方收到后仍用同一个纯规则引擎验证合法性。消息具有严格递增序号和有界 ID，`expectedRevision` 必须等于本地 revision，`beforeHash`/`afterHash` 必须与规范序列化后的 SHA-256 一致。重复命令只返回幂等确认，不会再执行；乱序、缺号、非法着法、身份不符或 hash 失配会锁定棋盘输入并进入恢复或失败状态。

正常走子绝不接受对方发送的任意完整 `GameState`。恢复快照必须通过严格 schema、revision 与 position hash 校验，并且其规范命令日志必须是本地日志的严格前缀扩展；本地与远端已经分叉时拒绝覆盖。这一约束防止偶发乱序静默改写棋局，但不是反作弊机制。

单条棋局帧最多 16 KiB，手动信令文本最多 64 KiB；接收端还限制突发帧频率与待发送队列大小。所有 JSON 消息都使用精确字段 schema，未知字段、二进制帧、无效 UTF-8、未知协议版本和超限内容会被拒绝。

## 断线、刷新与存档

- 短暂掉线进入约 15 秒宽限期并立即锁定本地输入；连接在宽限期内恢复后会重新核对 revision/hash。
- ICE/连接失败、DataChannel 关闭或超时不会被解释成认输。对局保留为待重新配对状态，用户可再次走完整 Offer/Answer 流程。
- 页面隐藏时停止主动棋局操作并继续保留必要协议处理；重新可见时立即重新验证连接与棋局状态。移动系统可能直接挂起或回收标签页，因此不能把后台宽限视为可靠保活保证。
- 刷新页面会销毁 PeerConnection。存档保留棋局命令日志、身份、阵营和 rematch index，但不保留 SDP、ICE、PeerConnection、消息序号或待确认帧。恢复时必须重新配对。
- 重新配对后，双方通过 `hello` 比较 revision/hash。完全相同则继续；一方是另一方的规范严格前缀时，可请求并验证快照补齐；分叉、无法验证或协议版本不兼容时保持锁定，不能选择某一端强行覆盖。
- 认输与终局会写入规则状态。重开只有双方明确同意才切换到下一 `matchId`；若切换期间页面被关闭，旧终局存档仍是可解释的回退点，重新打开后需要再次配对。

## 隐私、安全与信任模型

WebRTC DataChannel 使用浏览器提供的 DTLS 加密传输，但手动信令文本本身不由本应用另行加密。Offer/Answer 包含临时 SDP、ICE candidates、证书指纹和会话标识，可能暴露局域网或公网网络信息；任何拿到有效文本的人都不应被视为可信旁观者。只通过信任的私聊传递，用后删除，不要截图公开。

配置第三方 STUN 意味着浏览器会向该服务发请求，服务运营方可以看到来源公网 IP、时间与请求元数据。首版不会把棋局命令上传到应用游戏服务端；复制、系统分享或聊天软件如何保存信令文本，受相应平台的隐私政策约束。

严格 schema、大小/频率限制、合法性复算和 revision/hash 核对主要防止故障、畸形输入和资源滥用。它们不能阻止好友使用修改后的客户端、读取本地棋局状态、调用分析引擎、拖延消息、故意断线或谎报其操作环境。因此此模式不提供防作弊、排名、公平竞赛裁决、观战审计或竞技级可靠性承诺。

## 首版不做与后续升级

首版明确不做：自动匹配、公开房间列表、账户/好友系统、服务器权威裁决、跨设备云存档、旁观、聊天、棋钟、悔棋、TURN 中继、自动 ICE restart，以及竞技反作弊。

房间码信令可以作为独立适配层加入：边缘服务只需临时保存带过期时间和单次消费语义的 Offer/Answer，提供限流、滥用防护和删除机制；棋局 DataChannel 协议不应依赖房间服务，也应继续保留手动文本回退。

TURN 也应独立配置：服务端签发短期凭证，客户端按策略添加 `turn:`/`turns:` iceServers，并配套带宽配额、区域、滥用与成本监控、隐私披露和故障回退测试。房间码与 TURN 可分别上线，不得成为首版手动直连的隐式依赖。

## 发布验收清单

- 默认构建看不到在线入口；显式开启 feature flag 后入口、创建/加入与重新配对文案可见。
- 两个相互隔离的浏览器上下文能够完整交换 Offer/Answer、双方准备、红方走子、黑方走子、任意轮次认输与重开换边。
- 非法、重复、乱序、超大、超频、版本不兼容和 hash 失配消息不会改变权威棋局，且会给出可解释的锁定或失败状态。
- 刷新任一端不会静默续用旧连接；重新配对只能恢复相同状态或严格前缀，分叉存档必须拒绝。
- 连接失败、取消、组件卸载和重开都会释放 PeerConnection、DataChannel、监听器与定时器，并清除信令文本。
- 无 TURN 的限制、信令敏感性、第三方 STUN 边界和无防作弊承诺同时出现在产品界面与本说明中。
